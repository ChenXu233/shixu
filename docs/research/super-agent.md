DeepSeek 于 2026-10-31 发布设计文章《Super-agent 设计探索：迈向更自主的 Agent 系统》与原型仓库 `dsh-superagent-prototype`（MIT，明确声明是技术路线验证，不是正式产品）。本文只做两件事：把它的架构说清楚，把它与我们逐条对照。

## 它是什么

### 四项特征

| 特征 | 含义 |
|---|---|
| 连续 | 用户可以在即时通讯、GitHub 评论等不同渠道与同一个 Agent 交互 |
| 高效 | 并行处理多个复杂任务，不因单会话阻塞 |
| 主动 | 持续观察环境事件，自行推进值得处理的事项 |
| 持久 | 始终在线，长期运行中能从异常状态恢复 |

出发点是：单任务已经不太需要人盯着，瓶颈转到了**人的注意力**；而主流 Agent 仍以单一 Session 为单位，人同时只能跟进 3 至 5 个活跃会话。

### 五部分架构

| 部分 | 做什么 |
|---|---|
| 双层架构 | **Router** 承接人类交互、维护全局上下文并分派任务，统一对外沟通；**Worker** 在相互隔离的会话中并发执行，不直接回复用户，只把状态与结果汇报给 Router |
| 事件驱动 | 外部事件称 **Trigger**（群消息、邮件、日程、代码审查评论、CI 结果）；先由程序规则粗筛，再交模型判断是否需要行动。已分配任务的事件流，Worker 直接订阅对应 **Thread**，后续事件绕过 Router |
| 面向人的交互 | **异步 ReAct Loop**：耗时工具调用改为 `start()` / `stop()`，返回 Started 即让出前台，结果稍后作为新事件进入会话。官方注明**已在 DSH 实现但尚未默认开启** |
| 计算与状态分离 | 计算与持久状态放云端，执行环境留在用户本地，只部署负责执行命令、回传结果的轻量 daemon；支持 **BYOM**（带自己的机器） |
| Watchdog | 主架构之外的独立 Session，构成外部控制回路：除基础设施故障外，还用模型判断 Worker 是否取得实质进展、方向是否偏离目标 |

### 上下文与投机

- **Inline & Spill**：近期可能用到的信息直接进窗口，超预算或低频内容留在窗口外按需读取。
- **Chain of Recall**：沿 Trigger / Thread / Worker Session 之间的引用关系，逐步找回历史任务信息。
- **投机执行**：依据环境信号在后台提前开工。例：收到会议邀约先查日程冲突、备好草稿；群聊讨论问题时先复现故障、找修复方案，确认可行才交付。

### 初步实验（合成负载，非真实能力评测）

| 口径 | 数值 |
|---|---|
| 负载 | 每次约 300 条消息，其中约 20 条为工作请求；每种方案重复 5 次 |
| Super-agent 任务完成时间 | p50 12.4 分钟 / p95 15.7 分钟 |
| 单 Session（中性提示） | p95 29.5 分钟 |
| Router 压力测试 | Trigger 到达 1 → 40 条/分钟时，批处理 1.0 → 2.8，单次请求 2.5 → 3.9 秒，单决定分摊推理 6.4 → 1.6 秒 |

作者自陈：这些实验主要评估**系统调度与协作能力**，不衡量单个任务的实际执行能力。

## 与我们的对照

| 维度 | Super-agent | 我们的设计 | 结论 |
|---|---|---|---|
| 跨渠道连续 | 同一 Agent 在 IM 群聊与 GitHub PR 之间连续推进 | 渠道内核 + driver，同一人格跨场所 | 印证 |
| 事件入口 | Trigger → 程序规则筛 → 模型判断 | driver 事件 → 内核去重限流 → 场所 → agent | 印证 |
| 对话单元 | Thread：同一话题或同一 PR 下的连续 Trigger | `venueKey`（platform / account / conversation [/ thread]） | 印证 |
| 对外沟通 | Router 统一对外，Worker 不直接回复 | 内核独占审批应答与发送，driver 不应答 | 印证 |
| 执行隔离 | Worker 在相互隔离的会话里并发 | 一场所 = 一 session + 一 agent | 印证 |
| 全局上下文 | Router 一个会话持有全局上下文 | 每场所各自上下文 + 记忆服务读穿 | **分歧** |
| 异常与偏离 | 独立 Watchdog Session，用模型判断是否跑偏 | 只有引擎内的预算与公平性规则 | **缺项** |
| 长任务 | 异步 ReAct（start/stop），Started 即返回 | `followup` 同步投递 | **缺项** |
| 安全与隐私 | 明列为待解：提示词注入、端侧凭据泄露、跨设备权限 | capability token + 凭据落位 + 可逆性判据 | **我们领先** |

### 三条结论

1. **方向一致，且我们正好落在「连续」这一项上。** 渠道内核 + 场所模型就是这条能力的实现，不是它的替代品 —— 它管的是 Agent 系统内部的分工，我们管的是接入与人格。
2. **一处真分歧，两处缺项。** Router 用单一会话持全局上下文，我们用每场所独立上下文 + 共享记忆读穿：他们换全局一致性，我们换抗上下文膨胀与隐私分层，这是取舍不是对错，等真实负载检验。Watchdog 与异步工具调用我们确实没有。
3. **一处领先。** 他们把「云端 Agent 接入本地设备后的提示词注入、端侧凭据泄露、跨设备权限」明确列为待解决问题。我们的三块答案正好覆盖它（token 验签在服务端、凭据只落 `ctx.credentials`、判据按可逆性 × 影响半径）。

## 对本项目的影响（待验证，不是待办）

| 议题 | 现在的判断 | 何时再判 |
|---|---|---|
| 要不要 Watchdog | 我们的公平性与预算都是引擎内规则，没有独立的外部控制回路；长期自主运行时它可能比规则更容易发现「跑偏」 | 进入 P3 注意力与自主之前 |
| 要不要异步工具调用 | 现阶段 `followup` 同步投递够用；一旦有分钟级工具，前台就会被堵住 | 出现第一个长任务时 |
| 全局上下文放哪 | 维持现状（每场所独立） | 用真实多群负载对比一次 |
| 安全方案能否补位 | 能，但需要对方的场景清单才能验证；他们的三项风险我们都有对应设计 | 与真实本地 daemon 联调时 |
