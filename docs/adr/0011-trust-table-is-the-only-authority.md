# ADR-0011：权限只来自主人的信任表

> **状态**：`accepted`
> **日期**：2026-11-04
> **落地阶段**：P1
> **上游材料**：[身份与权限](../reference/contracts-persona.md#身份与权限)、[ADR-0007](0007-rbac-carries-authorization-and-risk.md)、[判据与默认值](../reference/policies.md)

## 背景

第一版权限实现里，角色的来源混了两样东西：主人名单，和平台报的角色（群主、管理员）。看起来省事——群里谁是管理员平台已经告诉我们了，何必再让人配一遍。

但这不是省事，是把**事实**当成了**授权**：

- 群主能管住那个群，那是 QQ 给他的权力，不是主人给他的；
- 主人根本不可能认识所有群的群主；
- 于是一个陌生人建个群、当上群主，就能让 agent 跑 bash、改文件、碰凭据。

另一半问题是归属。工具调用没有说明「这次是替谁做的」，就只能靠运行时记的「最近谁说过话」去猜。同一个群里两个人连着说话时，这个猜测会张冠李戴。

## 决策

### 一、角色只有一个来源：主人自己写的信任表

`$DSH_HOME/persona/<personaId>/identity.json`：

```json
{ "owners": ["1964324406"], "trusted": ["10001"] }
```

- `owners`：主人。跨场所，任何地方都是 `owner`。
- `trusted`：主人亲手放进去的人。跨场所，`trusted`。
- 其余所有人：`guest`。
- 没有发起人的回合（它自己决定做的）：`autonomous`。

平台报的角色**不参与判定**。它作为事实留在事件里（`Actor.role`），可能对社交判断有用，但不是授权。

### 二、guest 也能说话、也能让它干活

guest 不是「不许用」，是「只能用不会替任何人做主的那些」：聊天照常，只读的场所动作（看群成员、查资料）照常。可逆的写动作（禁言、改角色）只属于 `owner` 与 `trusted`。

按角色分的出厂矩阵：

| 角色 | 能用的东西 |
|---|---|
| `owner` | 全部（那是他的机器） |
| `trusted` | 这个场所的全部动作；碰不到主机上的工具 |
| `guest` | 只读的场所动作 + 聊天 |
| `autonomous` | 同 guest |

### 三、工具调用必须声明替谁做

生成的每个工具多一个必填参数 `principal`：说话人的用户 id，或 `self`（它自己决定的）。

判定三步：声明的人必须是**这一轮真的开过口的人**（不是「最近说过话」，不是「平台说是管理员」）→ 查出角色 → 按矩阵判工具名。

声明与事实不符就拒绝。这样模型替一个没开口的人做主时会被当场挡住，而不是悄悄替他把事办了。

### 四、不再一次只服务一条消息

第一版为了避开「同群人交错导致判定张冠李戴」，改成同场所一次只服务一条消息（等 `turn/end`）。那不是人：人是一边听一边想，几句话合起来答。

现在说话人按**回合**记：`user/message` 事件里出现过的消息才算这一轮的发起人，`turn/end` 清空。判定读的是这个集合，不读「最近谁说过话」。于是串行队列可以去掉，两条消息同时进来也不会互相张冠李戴。

## 后果

- 部署后必须在 `identity.json` 里写主人的平台用户 id，否则所有人都只是 guest —— **默认安全，默认也不好用**，这是刻意的。
- 主人改信任表不用重启：每条消息投递前重读一次。
- 平台管理员在人格眼里没有任何特殊地位。若某个群的管理员确实要能指挥它，主人把他写进 `trusted`。
- `member` 这个角色从种子里去掉：它原本的含义是「平台意义上的普通成员」，而现在没有平台角色参与判定，它和 `guest` 无法区分。
