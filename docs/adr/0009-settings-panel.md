# ADR-0009：配置走设置页，同一份数据两个入口

> **状态**：`accepted`
> **日期**：2026-11-01
> **落地阶段**：P2
> **上游材料**：[DSH 接缝](../reference/dsh-seams.md)、[渠道内核契约](../reference/contracts-channel.md)、[决策 0005](0005-driver-per-protocol.md)

## 背景

驱动的参数现在只有一个入口：profile 的 `cordis.patch.yml`。五件事都得改文件才动得了——连接方向、地址与令牌、用哪个模型、哪些群启用、哪个角色能调什么工具。

代价不在写 YAML 本身，在于：改一次要进容器、要重启、要记得 patch 的合并语义；而且使用者是没有源码的那一半人，他们只有浏览器。

DSH 的 Web UI 里已经有设置页，并且**允许插件注册自己的分区**（`settings.section` 槽位，`dsh-client-ui-settings-models` 等六个包都在用）。所以问题不是"能不能有界面"，而是"界面和文件谁是真相"。

## 决策

**面板是编辑器，不是第二份配置。**

| 决策 | 内容 |
|---|---|
| 数据源唯一 | GUI 读写的对象就是 profile patch 里那一行的 `config`。没有 `settings.json`，没有插件私有存储 |
| 落点 | DSH 设置页的一个分区（`settings.section`），**不占**主页侧边栏、不占 `main`、不注册 `sidebar.panellist` |
| 读写通道 | 读 `ctx.remote.settings` 的视图，写 `mutate(ns, ops, revision)`；`ns` 就是插件行的 id |
| 客户端形态 | 单文件 `client/client.js`，手写 `React.createElement`，用 `window.__ModuleLoader__.load` 注册。**v1 不引入打包器** |
| 分发 | 文本全部走 locale 服务，中英各一份；不含任何个人值（地址、令牌、群号），开箱是空表单 |

两个入口写同一份数据，所以不存在"GUI 改了但文件没变"或"文件改了但界面不刷新"——它们本来就是同一个东西的两种看法。

## v1 只做有状态的三个分区

| 分区 | 字段 | 为什么在 v1 |
|---|---|---|
| 连接 | 方向（反向 / 正向）、URL 或 `host`+`port`、令牌、平台 | 没这个参数就起不来，且换环境必改 |
| 模型 | 跟随默认 / 指定 `provider` + `model` + `effort` | 人格需要一个模型；跟随默认让它不绑死 |
| 场所 | 启用列表、每个场所的角色名 | 一个号在多个群，得能逐个开关 |

角色到规则的映射（`PermissionRule` 表）v2 再进面板：它是一张二维表，编辑体验和上面三项不是一类问题，硬塞进 v1 会把面板做成表格编辑器。

## 驱动要补的一件事：正向连接

现在只有反向：我们监听，NapCat 连过来。但"网络只允许出站"是真实存在的环境——比如部署在只给出站的企业网里。

所以 `dsh-shixu-driver-onebot11` 要有两种传输：

| 方向 | 谁连谁 | 配置 |
|---|---|---|
| 反向（现状） | NapCat → 我们 | `host` + `port` + 令牌 |
| 正向（补） | 我们 → NapCat 的 WS 服务端 | `url` + 令牌 |

面板的"方向"选择器直接决定这两组字段哪一组可见。这属于**协议驱动**的事，不是渠道层的事——渠道层看到的仍然只是归一化后的事件。

## 被否决的替代

| 替代 | 否决理由 |
|---|---|
| 只用原生配置表单（插件导出 `Config`，`.volatile()` 字段自动成表单） | 零前端代码，但它只能表达"值"。连接状态、方向切换后字段组的变化、场所列表都表达不了；而且用户看到的是一张由 schema 生成的表，不是一个能读懂的产品界面 |
| 面板放进 `sidebar.panellist` / `main` | 设置是低频入口。做一个主页去装五个开关，等于用高频位置承载低频动作 |
| 插件自建 `settings.json` | 第二份真相。只要它和 patch 同时存在，就必须回答"谁覆盖谁"，而这个问题的每个答案都会在某个时刻静默生效 |
| 让面板直接改仓库里的 `cordis.patch.yml` 文件 | 那是 bundle 里的模板，不是某个部署的配置；改它对已经装好的 profile 没有影响 |

## 后果

- 多一份要维护的浏览器产物。它跟随 DSH 的 Client API 走，升级时要回归一次。
- 配置的**唯一落盘位置**仍是 profile patch，所以备份、迁移、把它抄给别人的方式不变：还是那个文件。
- `Config` 仍然要声明（volatile），否则 host 侧不知道有哪些字段、也没法校验；面板只是它的编辑器。

## 未决

- 场所列表的数据从哪来：驱动上报（连上就知道有哪些群）还是人工填。前者准，但要等驱动连上；后者在没连上时也能配。v1 先做人工填 + 连上后回显对账。
